# 上财 150 问覆盖评测可视化设计

## 目标

在现有 FastAPI 应用中增加 `/coverage` 页面，把
`data/coverage/sufe_coverage_after.json` 中固定 150 问的检索评测结果完整、可追溯地展示出来。
页面首先服务于数据质量审计，而不是只展示一个好看的通过率：用户必须能从场景总览下钻到每一道题，核对命中文档、部门、文档类型、版本状态、附件状态、回答要点证据、置信度和缺失原因。

本次只读取已有评测产物，不重新执行检索，不修改题库，也不改变评测状态。

## 入口与数据边界

- `GET /coverage`：返回独立的评测仪表盘页面。
- `GET /api/coverage`：读取并返回当前 `sufe_coverage_after.json`。
- `/` 与现有问答界面保持不变；两个页面在页首提供互相跳转入口。
- API 路径由应用配置中的 `data_dir` 推导，测试可以注入临时数据目录。
- API 仅暴露报告中已有字段，不在前端重新推断 `answerable`、版本有效性或权威来源。
- 报告不存在、JSON 损坏或结构不完整时返回明确错误状态；页面显示可恢复的错误说明，不伪造空数据。

## 页面信息架构

页面采用“质检卷宗 + 150 格证据矩阵”的视觉隐喻，与现有“红头档案”界面保持同一套纸张、朱红、墨色语言，但布局针对大规模审计优化。

### 1. 卷宗页首

显示标题“150 问覆盖质检”、评测时间、题库版本、题库哈希、索引指纹与检索配置。长哈希默认缩写，悬停或点击可查看完整值。

### 2. 核心指标

从 150 条逐题结果实时汇总：

- 总问题数；
- 完整可回答数与比例；
- 部分可回答数与比例；
- 不可回答数与比例；
- 权威部门命中数；
- 含附件问题数。

所有比例以固定题库总数为分母。页面不把 `partially_answerable` 计入完整通过率。

### 3. 场景覆盖条

按报告中的 11 个场景展示堆叠覆盖条，区分完整、部分和不可回答。每个场景同时显示 `完整数 / 总数`，点击后筛选问题矩阵。排序默认沿用题库场景顺序，不按通过率重新排序，便于前后报告对照。

### 4. 150 格证据矩阵

每个问题对应一个带编号的小方格：

- 深绿色：`answerable`；
- 琥珀色：`partially_answerable`；
- 朱红色：`not_answerable`；
- 方格角标提示附件与版本不明风险。

矩阵必须完整容纳 150 题，并支持按场景、状态、是否含附件筛选以及按问题、ID、标题、部门和 doc_id 搜索。筛选时显示“当前 N / 150”，同时保留题目在固定题库中的原序号。

### 5. 问题审计列表

矩阵下方用紧凑列表展示筛选结果。每行包括固定序号、问题 ID、问题正文、场景、状态、首个命中文档和缺失要点摘要。点击矩阵方格或列表行打开同一详情面板。

### 6. 逐题证据面板

详情面板展示：

- 问题 ID、问题、场景和最终状态；
- 命中文档表：doc_id、标题、发布部门、发布时间、文档类型、有效性状态；
- 是否命中预期部门、匹配域名和是否含附件；
- 每个 `required_answer_point` 的支持状态；
- 证据 doc_id、证据片段、判定理由、检查器和置信度；
- 缺失原因。

证据片段保留原文，不由前端润色。缺少某字段时显示“报告未提供”，避免把未知显示成通过。

## 交互与 URL 状态

- 搜索和筛选即时生效，不请求后端二次评测。
- 当前问题使用 `?question=<id>` 写入 URL，刷新后可以恢复并便于分享定位。
- `Escape` 关闭详情面板；桌面端为右侧抽屉，窄屏为整页底部面板。
- 所有状态不只依赖颜色，还提供文字和图形标记，保证色觉障碍用户可辨识。
- 问题方格、筛选按钮和抽屉均支持键盘操作并提供可见焦点。

## 前端实现

新增独立静态文件：

- `coverage.html`：语义结构和加载骨架；
- `coverage.css`：页面专属样式；
- `coverage.js`：取数、派生统计、筛选、矩阵和详情渲染。

不引入前端框架或图表依赖。场景覆盖条和矩阵使用原生 HTML/CSS，减少构建和部署复杂度。动态文本一律通过 DOM `textContent` 写入；不得把报告内容直接拼接为不受控 HTML。

## 后端实现

在 `create_app` 中新增 `/coverage` 与 `/api/coverage`。API 读取文件时完成最小结构校验：根对象必须包含 `question_results` 数组和 `scene_stats` 对象，每道题至少包含 `id`、`question`、`scene`、`status`。合法状态显式限制为：

- `answerable`
- `partially_answerable`
- `not_answerable`

API 返回 `Cache-Control: no-store`，确保重新运行评测后刷新页面即可看到新结果。读取失败用适当 HTTP 状态码和稳定的 `detail` 消息返回。

## 视觉方向

延续现有档案系统的纸张底色和朱红强调色，但避免通用蓝色 SaaS 仪表盘：

- 页面背景表现为质检卷宗纸面；
- 标题使用宋体风格，数据和 doc_id 使用等宽字体；
- 150 格矩阵是页面的主视觉签名；
- 状态色只用于结果编码，不做大面积装饰；
- 图形无渐变、无 3D、无外部图片依赖；
- 桌面和移动端均可完整审阅 150 题。

## 测试与验收

后端测试：

- `/coverage` 返回页面；
- `/api/coverage` 能从注入的数据目录读取报告；
- 报告缺失、JSON 损坏、字段缺失和非法状态均返回明确错误；
- API 不触发 embedding、检索或 LLM 初始化。

前端验收：

- 首屏统计与 JSON 的 150、85、65、0 一致；
- 11 个场景数量总和为 150；
- 状态筛选、场景筛选、附件筛选和全文搜索可组合；
- 任一问题都能打开详情并查看 doc_id 与逐要点证据；
- `?question=jwc-leave-001` 可直接定位对应题；
- 报告加载失败时显示错误态；
- 360px 宽度下无横向页面溢出，键盘可遍历主要交互。

## 非目标

- 不在页面中重新运行 150 问评测；
- 不允许在页面中编辑问题、expected_doc_ids 或判定状态；
- 不把自动覆盖探针升级为人工金标准；
- 不在本次加入历史趋势图，因为当前报告未形成稳定的时间序列；
- 不修改现有抓取、索引、检索阈值和问答链路。
