# 公众号对照审计：发现与决策

## 用户优先级

1. 数据质量。
2. 维护与更新的易用度。
3. 非专业人士能快速上手管理维护。
4. 产品应有学生问答端与管理员治理端两个明确角色；管理员用可视化 Dashboard 管理文档，并查看入库时间线与分类。

## Steelman 后的产品意图

- Dashboard 不是装饰性报表，而是知识库控制面：管理员要知道“现在有什么、为什么可信、哪些不可用、最近变了什么、发布前是否安全”。
- 文档管理至少包含列表/搜索/筛选、来源与时间证据、分类/生命周期/质量状态、正文详情、隔离/恢复等可逆治理动作；直接永久删除不是首版默认操作。
- 时间线应表现真实 `fetched_at`/`publish_date` 与新增/更新状态，分类图应能反向筛选文档，不能只是静态图。
- 可部署意味着管理员入口默认受保护；不能把写操作裸露在公开学生站点。无管理凭据时应保持只读或拒绝管理 API。
- 非专业维护者需要界面内行动提示、结果反馈与恢复路径，而不是暴露 `doc_id`、collection 名和内部 gate 术语。

## 已知仓库状态

- 当前 `master` 工作区存在大量用户未提交的代码、语料、索引和报告变更，后续只做边界清晰的增量修改。
- 根目录已有另一项“问题覆盖驱动采集”规划；本任务使用独立 `.planning/wechat_quality_maintainability/` 记录，避免覆盖。

## 外部文章发现

- 用户已直接提供公众号文章全文，原文需求现已可核验；此前网页访问限制不再影响需求判断。
- 大赛明确“不以功能数量和技术复杂程度作为唯一标准”，更关注是否真正减少学生校园信息检索和政策理解成本。
- 基本要求依次强调：真实校园需求、权威可靠知识来源、来源清晰可追溯、交互清晰友好；官方来源明确包括校/院官网、官方微信公众号、职能部门通知/制度/办事指南。
- 评审维度原文顺序为：校园实用性、回答准确性、知识库质量、回答与原始资料关联度、交互体验与界面美观度、学生体验反馈、创新性与完整度。
- “知识更新和分类方式是否合理”属于知识库质量的显式评审项，管理员 Dashboard 的时间线、分类与发布状态因此是核心治理能力，不是额外装饰。
- 特别提醒禁止虚假、未经核实、侵权、个人隐私、账号密码或敏感信息进入公开平台，并要求评审期间体验链接持续可访问。
- 提交材料包含知识库来源清单、使用说明、演示材料和学生反馈；Dashboard 可直接支持来源清单与演示截图，但不能替代真实学生反馈收集。
- 普通网页读取此前未返回正文。
- in-app/扩展浏览器发现结果为空，当前环境无可用浏览器实例。
- 下一步优先检查仓库中该文章 ID 的既有抓取记录，再尝试只读 HTTP 获取；无法验证的文章内容不作为改动依据。
- 仓库设计文档把该固定文章 ID 标注为上海财经大学计算机与人工智能学院“校园问答智能体开发大赛”公告，项目目标与文章确有直接关联。
- 用户已在本机浏览器打开文章，但当前会话重新发现目标 URL、连接扩展实例均返回无可用浏览器；这是连接边界，不是页面内容判断。
- 精确文章 ID、赛事标题、SUFE 域名三组公开搜索均未返回可用结果；HTTP 原文落在微信“环境异常/去验证”页。
- 仓库旧设计规格将评审优先级二次概括为“准确性优先”，与原文列示顺序不完全一致；后续产品判断以用户提供的公告全文为准。

## 本地实现发现

- 仓库已有来源配置、网页/附件/微信采集、清洗入库、版本关系、质量审计、覆盖评测、索引、检索、生成与 Web UI，不能另起一套维护系统。
- 已存在微信专用实现和测试、权威来源 YAML、语料 manifest、质量报告与覆盖报告；改进重点应是把这些现有能力收束成易懂入口，并补齐缺失门禁。
- 工作区的这些相关文件多数已有未提交改动，编辑前必须逐文件查看 diff。
- 直接引用公告的已批准设计规格明确评审优先级为：回答准确性 > 来源可追溯 > 知识库质量 > 校园实用性 > 交互体验 > 创新性；本次用户给出的优先级与原始项目目标一致。
- 设计规格要求官网抓取与 `data/inbox/` 手动投放双入口、`content_hash` 增量更新、隐私扫描、固定评测集和不达标门禁；这些不是新增愿望，而是既有验收标准。
- 当前 README 面向开发者列出大量架构细节和 20 余个 CLI 子命令；非专业维护者仍需理解来源类型、category、抓取/入库/索引/评测之间的先后关系。
- README 的日常更新 Happy Path 仍是多条独立命令，没有“预检 → 更新 → 质量报告 → 索引 → 验收”的统一入口，也没有失败后该看哪个报告的操作手册。
- CLI 已有 `crawl-authoritative`、`ingest`、`quality-audit`、`quality-gates`、`index`、`eval` 等可复用原语，最小方案应编排现有命令，而非重写爬虫或新建管理后台。
- `data/inbox/` 手动入口目前要求操作者在命令行提供 `--category`；README 只给一行示例，缺少文件投放模板、分类说明、预览/验收和常见错误指引。
- 当前 manifest 物理上有 4,623 行、2,532 个唯一 `doc_id`；它是 append/last-wins 日志而不是“当前文档清单”。直接数行会把历史状态重复计数，维护界面和质量摘要必须使用 `load_manifest()` 的 last-wins 视图。
- 全部物理记录都有来源 URL、发布日期、抓取时间；有 1,464 条旧日志记录缺 `content_hash`，需在 last-wins 视图中复核后才能判断是否仍影响增量更新。
- 当前原始行中 `quality_status=accepted` 4,096，但这也包含同一文档历史状态；给非专业人员展示该数字会误导，必须输出“当前唯一文档/可检索文档/隔离文档”三个口径。
- 现有 `quality-audit` 已按 last-wins 计算生命周期、年度系列、collection 污染、附件依赖和 raw 可恢复性，能力较强；但 Markdown 主体是逐文档长表，缺少按严重度排序的“现在该做什么”。
- `validity_status=unknown_validity` 在物理 accepted 记录中占绝大多数；该字段只在有明确正文证据时赋值，不能把 unknown 一刀切判为错误，应结合 `retention_status`/年度生命周期解释。
- 按 last-wins 当前视图：2,532 篇唯一文档，2,111 篇 accepted；其中 1,011 篇带完整文件路径/hash 且被分配到 main/public/historical collection（570/226/215）。这 1,011 才接近当前可检索口径。
- accepted 中有 868 篇无正文文件/hash，多数是已归档但保留审计元数据；它们不应被称为“可用知识”，但也不应简单删除。面向维护者的摘要要把“审计留档”与“在线可答”分开。
- 当前 1,521 篇 `index_collection=none`、788 篇 `document_kind=incomplete`；隔离机制在工作，但必须把主要拒绝原因和待处理数量汇总出来，避免坏数据静默堆积。
- 最新现存质量报告的 manifest 指纹均与当前 `sha256:547098...` 不一致；最近报告评估于 2026-08-12，当前数据已经变化。报告目前可以过期却没有醒目标识，这是维护流程的首要缺口。
- 2026-08-12 报告仍有 2 篇 collection 污染、751 篇无法分类、738 篇归档且无 raw；需要运行当前审计确认，不能沿用旧报告宣称质量达标。
- `quality-gates` 会直接核验正文 hash、缺文件、collection 类型/生命周期、附件引用、重复 active 年度系列、固定题库与真实回答，但它与 `quality-audit`、索引、`eval` 分散为独立命令。
- `quality-gates` 会校验真实回答报告与覆盖报告彼此的题库/index 指纹一致，但未把二者的 `index_fingerprint` 与当前索引元数据再比较；两份彼此一致但共同过期的报告理论上仍可能通过。
- 质量门 JSON 没有 manifest 指纹；旧门禁报告仅凭文件名无法判断相对当前语料是否过期。应在现有报告中加入当前 manifest/index 身份，并在维护摘要显式标红 stale。
- 当前 README 与 CLI 的未提交 diff 是用户正在开发的微信公众号接入；后续修改需避开/保留这些 hunks，不能把它们当基线重写。
- 当前索引元数据的 `manifest_fingerprint` 与 manifest 完全一致，说明索引本身不是 stale；问题集中在质量/覆盖报告的可见新鲜度，而不是盲目要求全量重建索引。
- 索引元数据已经提供当前 `index_fingerprint=sha256:2c86e3...`，可直接复用来阻止共同过期的覆盖/真实回答报告，无需设计新指纹算法。
- 仓库已有可执行 `.venv/bin/sufe-qa`；本次验证可绕开全局 `uv` 缓存权限问题，后续维护指南也可提供 `uv run` 与本地入口的故障替代说明。
- 2026-08-20 fresh audit 已生成，指纹与当前 manifest 一致：2,532 总文档、1,243 有正文、1,006 active、231 historical、1,295 archived；主问答/公示/历史候选为 764/242/231。
- 当前审计的关键异常：6 篇 accepted+有正文却未进入任何 collection、5 篇正文明确依赖附件但没有有效附件、8 篇按时效策略缺可靠发布日期；active 年度系列重复与日期冲突均为 0。
- 794 篇 `incomplete` 中大量是已隔离的旧栏目页/新闻/低质附件，说明“隔离”有效；非专业摘要应将其列为已阻断，而不是把 794 全部渲染成紧急故障。
- 740 篇归档元数据缺 raw，多为历史迁移遗留；这影响可恢复性，不直接污染在线检索。升级优先级应低于 6 篇 collection 污染与 5 篇附件缺失。
- 421 个年度系列中 125 个存在历史多版本，但 active 重复为 0，说明保留历史并不等于重复污染；质量指标要避免把正常版本史标红。
- 6 篇污染候选由 1 篇缺可靠日期的手工转专业细则 + 5 篇“正文要求见附件但附件缺失”组成；后 5 篇目前 manifest 仍标 accepted/annual_notice，fresh audit 才把它们重分类为 incomplete。仅看旧 manifest/index 元数据会漏掉这类退化。
- 5 篇附件缺失中 4 篇是 2026/2027 推免预报名重要时效文档（含微信与学院官网），属于高价值但证据不完整的数据；正确动作是隔离并定向补附件，不是继续让正文进入主问答。
- 当前索引 fingerprint 为 `2c86e3…`；最新覆盖报告为 `da2286…`，真实回答报告为更早的 `545329…`。现存 `sufe_full_report.json` 却记录 `passed=true`，实证确认“共同/分别过期的评测可继续显示通过”是现有门禁漏洞。
- 因覆盖报告与真实回答报告本身 fingerprint 不同，当前 `quality-gates` fresh run 应失败 `real_answer_integrity`；即便未来二者一致，仍必须新增与当前 index 的比较。
- Fresh `quality-gates` 已实跑并失败 5 项：2 个正文 hash 不一致、51 个“当前 manifest 视角下应隔离却仍有正文”的文档、2 个 active 年度系列重复、5 个附件引用缺失、覆盖/真实回答 fingerprint 不一致。
- `valid_body_ratio` 目前算成“所有有正文文档 ÷ retained 文档”，当前得到 104.19%；分子口径错误会让此门永远偏乐观。应改为“retained 且有正文 ÷ retained”。
- `collection_isolation=true` 说明上述 51 个 corpus 文件当前没有污染 Chroma collection；这是离线语料状态未收敛，不是线上检索已经全盘污染。仍应在维护发布前阻断。
- 当前附件解析成功率约 79.7%（495/621）；其中很多 unsupported/scanned 是可解释隔离，但 5 个“正文依赖附件”是明确完整性错误，应单列 P0。
- 当前覆盖报告为 90/150 answerable、60 partial、0 not，权威域命中 150/150；但报告 fingerprint 落后当前索引，因此这些比例只能当历史基线，不能当今日验收。
- 现存 gate 输出只给英文内部 gate 名与 doc_id，非专业维护者不知道文件路径、原因和修复命令；需要中文行动摘要，而不是再加一个可视化后台。
- 两个 hash 错误分别是“本科导师选择规则调整的通知”和“经济学院本科学生毕业论文管理规定”；二者当前 `index_collection=none`，暂未进入线上 collection，但会阻断 corpus integrity。
- 现有 `rebuild-clean-corpus` 已具备所需根治路径：审计指纹锁防并发、staging 校验、原子切换、旧 corpus 带时间戳备份，并在复制保留正文时重算 hash；无需另写修复器。
- 清理命令也会把 fresh audit 的文档类型/生命周期/collection 决策写回 last-wins manifest，因此理论上可同时收敛 6 个污染候选、2 个 hash 错误和当前 manifest 生命周期陈旧问题。
- `ingest_inbox` 已有分类白名单、敏感信息隔离、内容 hash 去重、损坏文件跳过和同文件名原地更新；数据边界验证不能删减。
- inbox 目前只扫描根目录文件，category 必填且整批统一；为非专业人员新增复杂自动分类风险大。更稳妥的最小方案是提供明确分类表、投放清单和一个统一的检查/发布命令。
- 原子清理 dry-run 确认：保留 1,237 份正文、归档 1,295 条元数据；当前 1,243 份正文中仅 6 份会从在线 corpus 移出，范围与 fresh audit 的 6 个污染候选一致。
- 两个 hash 错误文件都是当前工作区新增、未跟踪文件；清理会保留正文并重算 manifest hash，不会回退用户内容。
- 原子清理已成功应用，旧 corpus 位于 `data/.corpus.previous-20260820T031445Z-828718bc`；这是物理数据清理的恢复点。

## 技术决策

| 决策 | 理由 |
|---|---|
| 先测现有入口与数据，再决定改动 | 避免为已有能力重复造轮子 |
| 不全量重建索引 | 当前索引 manifest 指纹与语料一致；全量重建成本高且无证据必要 |
| 管理端沿用 FastAPI + 原生 HTML/CSS/JS | 现有产品无构建链，原生栈已具备覆盖 Dashboard；避免再引入前端框架 |
| 管理 API 使用独立 Bearer token | 公共学生端不能继承写权限；无 token 时拒绝读取管理数据与动作 |
| 首版治理动作为可恢复隔离/恢复 + 显式发布索引 | 满足实际文档治理闭环，避免不可逆删除与编辑正文带来的数据损失 |
| 时间线读取 append-only manifest 历史 | 同一 `doc_id` 的首行/后续行天然对应新增/更新，不需另建事件数据库 |

## 管理端设计系统

- **主题：** 上财知识库管理员的“馆藏账本”，单一任务是判断资料能否安全进入学生问答。
- **色彩：** 档案墨蓝 `#14283b`、票据青绿 `#2e6b5c`、朱砂预警 `#a63d2f`、纸面灰白 `#f2f4f1`、铅灰 `#66737c`、索引金 `#b8892d`。
- **字体：** 标题用宋体/`Noto Serif SC` 的档案感；正文用 `Noto Sans SC`/系统黑体；doc_id、日期和 hash 使用等宽字体。
- **布局：** 左侧窄“档案索引”导航；主区依次为发布状态、入库时间脉冲、分类带、筛选账本；文档详情从右侧抽屉展开。
- **记忆点：** 入库时间线不是折线图，而是日期戳式脉冲带；点击某日直接筛出当天新增/更新的每份文档。
- **自检修正：** 删除通用 KPI 大卡片和饼图，改用“可发布/待治理/已隔离”的账本口径；所有可视元素必须能反向筛选文档或触发治理动作。
- 数据清理实现存在时间语义 bug：清理后 2,532 篇 current 文档全部显示 `2026-08-20`，备份中的真实 last-wins 分布为 2026-08-11（1,704）、08-13（471）、08-12（357）等。Dashboard 开发前必须先修复，否则时间线是伪数据。
- 该 bug 已修复并回归：`rebuild-clean-corpus` 现在保留原 `fetched_at`；重跑后分布仍为 08-11（1,704）、08-13（471）、08-12（357），迁移日记录数为 0。

## 遇到的问题

| 问题 | 解决方案 |
|---|---|
| 公众号链接无法通过网页工具读取，且无浏览器实例 | 检查本地抓取证据并尝试只读 HTTP；明确区分已验证内容与推断 |
| `uv run` 在解释器缓存临时路径遇到权限错误 | 网页只读解析换用系统 Python；项目环境作为独立维护性风险验证 |
| 用户打开页面后扩展和 URL 发现仍返回无浏览器 | 不再重复连接参数；转读仓库引用文章的原始设计资料，文章直读限制明确保留 |
